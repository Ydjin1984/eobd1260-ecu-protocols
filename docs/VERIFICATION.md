## 1. Подтверждено (выборка с доказательствами)

- **Транспорт**: `EOBD1260.exe` импортирует из `ftd2xx.dll` ровно 13 функций,
  состав совпадает со списком, `FT_SetBitMode` отсутствует (свой PE-парсер,
  т.к. DOS-stub вырезан LordPE).
- **База 05-spec**: 178 протоколов (id 0…182), у 177 — по 7 примитивов
  (id=182 — fallback-ветка), VMT 177 классов в `.rdata` `0x6206FC…0x62423C`
  (у id=182 — `0x6202F4`, вне диапазона), 911 функций с кадрами, 169 протоколов
  с распознанными кадрами. Инварианты кадров (`len == len(template)`,
  `known == число констант`) соблюдены во всех 2913 уникальных кадрах.
- **Сверка базы с бинарём (IDA)**: VMT классов id=0, 1, 11, 16 — все 28
  примитивов совпали с адресами из базы побайтово; `switch`-блоки фабрики
  `sub_5703B0` ↔ база: 178/178 id, 0 расхождений конструкторов.
- **Защита**: `Check0` в `winmap.dll` — буквально `{ dword_1000F994 = 1; return 1; }`;
  `.protect` = 1.46 МБ, энтропия 7.999; HASP-строки (`hasp_login`,
  `classic_key_info`, vendor-строка HASP зареджена), `HaspDecrypt/HaspEncrypt`,
  список анти-отладки (`smartchk`, `procdump`, `pdumpnt`, `td32`) — все на месте.
- **Чексумма**: `sub_4018C0` — XOR первых `n−1` байт в последний, как заявлено.
- **RX-буфер**: `memset(this + 2424910, 0, 0x400)` в `sub_403720`/`sub_4030E0` —
  1024 байта по смещению 2424910 (= `0x25004E`, не `0x25000E`, см. §3).
- **Кадры id=0 (BMW DDE4.0)**: `27 01`, `27 02 42 4D 57 17` («BMW»), erase
  `09 31 02 08`, close `B8 12 F1 03 30 EB 01 82` — всё присутствует; ключ «BMW»
  жёстко прошит.
- **`apertura.dat`**: 7 секций с точными базами/счётчиками (`#swap` 16×8,
  `#siemens1` 24×8, `#siemens2` 6×8, `#boschme7` 1×8, `#EDC16` 4×8 при базе
  `0x6000`, `#EDC16` 3×5, `#ME9` 1×8).
- **`chk/*`**: 148 файлов (145 `.chk` + 1 `.gen` + `.ch1` + `.ch2`), байты 0–6 =
  `44 8B C3 D1 AD 8D 4C`, байт 7 ∈ `0x92…0x9B` (10 значений), ноль байтов `0x00`,
  энтропия 6.66–7.35, имена не встречаются в бинарях, строка `.chk` в EXE
  отсутствует.
- **`auto.dll`/`auto2.dll`**: не PE, текст CRLF, 320 записей (160+160); все
  154 имени профилей, что есть в базе, совпадают по id с сырыми таблицами
  (0 конфликтов).
- **Реплика**: `loader.py protocols|show|probe` работает; `Frame.render()`
  отказывается отправлять кадры с незаполненными рантайм-байтами (fail-safe
  подтверждён на `probe 0 --step seed-key`: все 4 кадра корректно пропущены).

## 2. Решённый открытый вопрос: формат `EOBD2_LOG/*.gal`

Ранее (FINDINGS §8.2): «логи зашифрованы, энтропия 7.95, ключ не вскрыт».
**Фактически: логи обфусцированы XOR с единственным байтом `0x1C` по всему файлу.**

Доказательства:
- 16-байтовые «пустые» логи после XOR: `82 12 F1 10 85 1A` + `FF×10` — валидный
  кадр KWP2000 StartDiagnosticSession (Fiat, tgt `0x12`, src `0xF1`);
- `_eobd2_3521629.gal` после XOR: `82 12 F3 10 85 1C` / `82 F3 12 50 85 5C`
  (запрос/ответ, адрес `F3`) и строки идентификации VAG-ЭБУ:
  `02810101611037374104`, `G4AS01M0  0.8l SmartEDG15C-5.1`, `G4AS11B0`;
- `_eobd2_1902026/1902028.gal`: VIN `W0L0TGF08X504419209133261` + блок
  идентификации Opel (`CKSIE`, `S98008X18XE1`);
- наблюдение исходного отчёта «повторы `E3`, `2C`» объясняется тривиально:
  `0xE3 = 0xFF ^ 0x1C` (padding), `0x2C = 0x30 ^ 0x1C` (ASCII `'0'`).

Уточнение чисел (заявление «7.95» не воспроизводится):
энтропия по 46 файлам — от 0 (пустые) до **8.000**; текстовые логи сессий
6.2–7.2, near-uniform 8.0 — это один бинарный лог (475 КБ, вероятно поток данных
флеша). Декодировано 15 логов с осмысленным содержимым; декодер — `tools/gal_decode.py`
(вендорские логи и их декодированные копии в репозиторий не входят).

**Ценность для проекта**: логи — это записанный реальный K-line трафик
(Fiat + VAG + Opel сессии). Их можно использовать как «золотой» материал для
валидации кадров базы (например, `82 12 F1 10 85 1A` из лога побайтово совпадает
с кадрами протоколов 19/26 и др. — см. §3).

## 4. Новые находки (помимо правок)

1. **Три «сиротских» профиля** (FAIL): `BMWMINID` (id=45), `SEATEDC15V` (id=56),
   `VWEDC15P` (id=27) есть в `auto.dll`/`auto2.dll`, но не сопоставлены ни одному
   протоколу. Причина: id **27, 36, 45, 56, 87 отсутствуют в фабрике** `sub_5703B0`.
   Гипотеза: эти ЭБУ обслуживаются не через протокольные классы (boot-mode/`chk`),
   либо ветки просто не скомпилированы в этой сборке. Для реплики это значит:
   3 профиля из базы ЭБУ отправить «своим» протоколом нельзя.
2. **Кандидат «ложной дырки» в базе**: в кадре write-block протокола id=0 байт
   позиции 2 помечен рантаймом (`B8 12 -- 09 34 …`), тогда как в псевдокоде
   `sub_43E3F0` рядом стоит `mov dl, 0F1h` и `v58 = -15` — то есть там, вероятно,
   **константа `F1`**, а не рантайм-значение. Требуется точечная ре-экстракция
   этого метода (ложные `--` заставляют реплику отказываться от отправки).
3. **Дубликаты профилей в базе**: `ecu_profiles` хранит каждый профиль дважды
   (слияние `auto.dll`+`auto2.dll` без дедупликации) — CLI печатает дубликаты,
   отчёты шумят. Косметика, но правится тривиально.
4. **CLI не умеет заполнять рантайм-байты**: `probe` умеет только полностью
   константные кадры; для реальной работы нужен способ передать адрес/seed
   (`--set b3=0x82 …`). Это осознанный fail-safe, но без него реплика
   простаивает на большинстве протоколов.
5. **Мелочь в коде**: `Frame.render(data=…)` без проверки границ может дать
   `IndexError` (в `loader.py`), и `probe` на шаге без кадров печатает ничего.
6. **Уточнена структура `chk/*`** (в дополнение к §8.1 FINDINGS): байт 7 ∈
   `0x92…0x9B` (10 значений, `0x93` ×30), байт 8 ∈ `{0x31, 0x54…0x5D}`,
   байты 10–23 → ровно 3 варианта (группы 117/16/15 файлов); первые байты
   `44 8B C3 D1 AD 8D 4C` похожи на x86-код (`mov r8d, ebx`), т.е. формат
   скорее бинарный, чем «шифртекст текста».

## 5. Сигналы Laya (вспомогательные, не вердикт)

Использованы `laya_health` / `laya_log_triage` / `laya_classify` / `laya_score` /
`laya_context_pick` (плагин davinci-laya-decisions, чекпоинт
`multilingual-fp16-0b095e005a4c`, ~90–150 мс на запрос):

- **log_triage** (ранжирование важности блоков): верх — подтверждённое ядро
  (0.92), 3 orphan-профиля (0.84), взлом `.gal` (0.83). Ошибку примера id=16
  Laya оценила низко (0.08) — но это ровно тот случай, где **детерминированный
  факт важнее Laya**: расхождение подтверждено псевдокодом, оставлено в списке
  правок.
- **classify** (тип находки `.gal`): `ошибка_вывода_отчёта` p=0.79,
  `ambiguous=false` — совпало с ручным выводом (данные целы, неверен вывод).
- **score** (готовность реплики к стенду): 1.66/3 — «нужны доработки до стенда»
  (p=0.46); согласуется с фактами: read-only шаги возможны для протоколов
  с полностью константными кадрами, запись — нет.
- **context_pick**: keep = результаты проверки, взлом `.gal`, обе фактические
  ошибки; архив = декодированные логи; on-demand = скрипт проверки.

## 6. Что осталось (рекомендации)

1. `chk`-файлы: формат по-прежнему не вскрыт, но структура уточнена —
   байт 7 ∈ `0x92…0x9B`, байт 8 ∈ `{0x31, 0x54…0x5D}`, байты 10–23 дают ровно
   3 варианта (группы 117/16/15 файлов), первые байты похожи на x86-код.
   Теперь есть декодированные логи — поискать в них имена `chk`-профилей и связь
   с `apertura.dat`.
2. Ре-экстракция `sub_43E3F0` (id=0 write-block) — проверить все `--` на
   «ложные дырки» (быстрый прогон: сверить `known` с числом констант по ASM).
3. Определиться с 3 orphan-профилями (id 27/45/56): искать обработчик вне
   фабрики или задокументировать как «не поддержано сборкой».
4. Дедупликация `ecu_profiles` + починка `probe` (заполнение рантайм-байт).
5. Стенд: начать с Fiat ME7.2.1 (id=16) или Peugeot EDC15C2 (id=19) —
   read-only идентификация по декодированным логам (в них есть ожидаемые ответы).

## 7. Артефакты проверки

```
tools/verify_claims.py     60 проверок, перезапускаемо (exit 1 при FAIL)
docs/verify-results.json   результаты по пунктам (59 PASS / 1 FAIL)
docs/VERIFICATION.md       этот отчёт
tools/gal_decode.py        декодер вендорских логов EOBD2_LOG/*.gal (XOR 0x1C)
```

Воспроизведение: распакуйте вендорский пакет EOBD1260 в любой каталог и
выполните

```bash
python tools/verify_claims.py <каталог_с_вендорским_пакетом>
```

База протоколов ищется как `05-spec/protocols-database.json`,
`spec/protocols-database.json` или `protocols-database.json` относительно
указанного каталога. Вендорские бинари и логи в репозиторий не входят.
