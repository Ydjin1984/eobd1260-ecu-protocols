# Handoff — EOBD1260 reverse engineering

Состояние на конец сессии. Проект: `C:\Users\lex66\OneDrive\Рабочий стол\EOBD1260`.
Рабочая копия анализа: `C:\eobd-re\` (там базы IDA и полный дамп дизассемблера).

## Что сделано

- Конструкторы 11 протоколов — тонкие обёртки (13 байт), настоящий конструктор
  стоит по адресу `обёртка + 0xD`; VMT разрешены скриптом `ida_fixvmt.py`.
- Транспорт: FTDI D2XX, K-line через RTS/DTR, 13 функций, класс порта
  VMT `off_624A24`. Реализован в `10-replica/src/ftdi_d2xx.py`.
- **178 протокольных классов** (id 0…182) — фабрика `sub_5703B0`, `switch (id)`.
  VMT в `.rdata` `0x006206FC…0x0062423C`, 7 примитивов на класса (`+8…+32`),
  транспорт на `+0x4C`.
- База ЭБУ: 320 профилей (`auto.dll` + `auto2.dll`, текстовые), 50 записей
  `Informazioni.txt` (таблица идентификации).
- **3066 кадров** извлечено из 911 функций; **177/178** протоколов с полным набором
  из 7 примитивов. База — `05-spec/protocols-database.json`.
- Инфраструктура: XOR-чексумма `sub_4018C0`, приём `sub_4030E0`, диспетчер
  KWP1281 `sub_4031D0`, буфер RX 1024 б по смещению `2424910`.
- Защита: HASP (vendor `qkBr…(reducted)`, рантайм в `winmap.dll`),
  `k.dat` = хеши трёх файлов, анти-отладка по именам процессов,
  `Gcheck.dll` — 1.46 МБ зашифрованного кода.

## Перепроверка 2026-10-14 (независимая ревизия)

Все проверяемые утверждения заново выведены из сырых артефактов
(`tools/verify_claims.py`, 60 автопроверок): **59 PASS / 1 FAIL**.
Полный отчёт — `docs/VERIFICATION.md`.

Главные результаты:

- **`.gal` вскрыты**: логи обфусцированы XOR 0x1C (не «шифр 7.95»).
  После декодирования — реальные KWP2000-сессии (Fiat `82 12 F1 10 85 1A`,
  VAG `82 12 F3 10 85 1C` + `SmartEDG15C-5.1`, Opel VIN). 15 логов декодированы (декодер — `tools/gal_decode.py`) — материал для валидации кадров базы.
- **Пример id=16 в FINDINGS §4 и README реплики был неверен**: кадр
  `82 12 F1 10 85 1A` принадлежит протоколам 19/26/49/59/61/67/74/75
  (подтверждено `sub_50E3D0`); у id=16 — короткие кадры `02 1A 98 00` и др.
  (исправлено в обоих документах).
- **База сверена с бинарём (IDA)**: VMT id=0/1/11/16 — все 28 примитивов
  совпали побайтово; `switch`-блоки `sub_5703B0` ↔ база 178/178;
  `Check0` — заглушка; `sub_4018C0` — XOR-чексумма. Всё подтверждено.
- **FAIL**: 3 профиля (`BMWMINID`/45, `SEATEDC15V`/56, `VWEDC15P`/27) не
  сопоставлены протоколам — id 27, 36, 45, 56, 87 отсутствуют в фабрике.
- Новые задачи: кандидат «ложной дырки» в write-кадре id=0 (сверить `known`
  с ASM); дедупликация `ecu_profiles`; CLI не умеет заполнять рантайм-байты.
- Laya (davinci-laya-decisions): триаж подтвердил приоритеты
  (ядро → orphans → gal), классификация `.gal` = «ошибка вывода отчёта»
  (p=0.79), готовность реплики к стенду 1.66/3 («нужны доработки»).



## Открытые задачи

1. **`chk/*.chk`** (148 файлов: 145 `.chk` + `.gen`/`.ch1`/`.ch2`) — формат не
   вскрыт, имена не встречаются в бинарях, строка `.chk` отсутствует. Гипотеза:
   читаются кодом из зашифрованной `.protect` секции `Gcheck.dll`. Зацепка:
   искать имена `chk`-профилей в декодированных логах (декодер —
   `tools/gal_decode.py`). Нужен динамический анализ.
2. **`EOBD2_LOG/*.gal`** — ✅ решено 2026-10-14: XOR 0x1C, логи декодированы
   (см. раздел «Перепроверка»).
3. **Рантайм-байты кадров** (`--` в базе) — читать псевдокод метода в
   `02-decompiled/dump/funcs/<функция>.c`. Кандидаты: id=19 (Peugeot EDC15C2 —
   канонический KWP2000, есть совпадающие декодированные логи) или id=16
   (Fiat ME7.3H4 — короткие кадры). Перед этим — сверка «ложных дырок»
   (`known` vs ASM).
4. **Профили без протокола**: `BMWMINID`/45, `SEATEDC15V`/56, `VWEDC15P`/27 —
   id 27, 36, 45, 56, 87 отсутствуют в фабрике `sub_5703B0`. Искать обработчик
   вне фабрики или задокументировать как «не поддержано сборкой».
5. **Стендовая верификация** — нужен ЭБУ на столе (12 В + K-line).

## Грабли

- **IDA `save_database(путь_входа)` перезаписывает сам бинарь базой.**
  Один раз это случилось с копиями в `C:\eobd-re\orig\` (восстановлены из
  OneDrive). Оригиналы в проекте не пострадали. Никогда не вызывать
  `save_database` с путём входного файла.
- `e_lfanew = 0x40`, DOS-stub вырезан LordPE, в полях стоит метка `LordPE]` —
  REA/Ghidra отказываются открывать файл как PE. IDA Pro 9.2 открывает нормально.
- MCP-провайдер Ghidra у REA сломан: `JAVA_HOME` указывает на JRE 17 вместо
  JDK 21+. Использовать `E:\REA\tools\rea.cmd` (там путь верный) или IDA напрямую.
