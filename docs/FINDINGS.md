# EOBD1260 — результаты реверс-инжиниринга

Полный статический разбор диагностического комплекса **EOBD1260** (Galletto 1260 / EOBD2,
итальянский ECU-флешер, сборка 2008 года). Цель — вытащить протоколы записи ЭБУ и
построить собственную реплику загрузчика под обычный K-line адаптер на FTDI.

Инструменты: IDA Pro 9.2 (Hex-Rays, headless), REA 6.3, Python.
Все адреса — виртуальные адреса образа `EOBD1260.exe` (ImageBase `0x00400000`).

## 2. Аппаратный уровень: как приложение говорит с адаптером

`EOBD1260.exe` импортирует из `ftd2xx.dll` **13 функций** — исключительно D2XX, без
виртуального COM-порта:

```
FT_OpenEx, FT_Close, FT_Read, FT_Write, FT_SetBaudRate,
FT_SetDataCharacteristics, FT_SetTimeouts, FT_Purge,
FT_SetRts, FT_ClrRts, FT_SetDtr, FT_ClrDtr, FT_ListDevices
```

`FT_SetBitMode` **не импортируется** — значит уровни K- и L-линии формируются
модемными линиями **RTS/DTR**. Для медленной инициализации (5 бод = 200 мс на бит)
и импульсов пробуждения этого достаточно.

### Класс последовательного порта

Методы найдены по вызовам (адреса проверены дизассемблером). Уточнение по итогам
аудита-2: `off_624A24` — **не** таблица методов порта; по этому адресу лежат данные
(double `1e-3`, строки `(nil)0123…`), а `*this = &off_624A24` — конструктор
вспомогательного класса `sub_574C70` (33 байта). Настоящий соседний VMT —
`off_624A30` (`DNameNode`). Таблица ниже — методы, реально вызываемые из кода
порта, без привязки к `off_624A24`:

| Метод | Адрес | Вызов D2XX |
|---|---|---|
| Open | `sub_574DB0` | `FT_OpenEx` (call site `0x574E0D`) |
| Close | `sub_574ED0` | `FT_Close` |
| Write(buf,len) | `sub_574F00` | `FT_Write` |
| WriteByte(b) | `sub_574F50` | `FT_Write` |
| Read(buf,len) | `sub_574F90` | `FT_Read` |
| SetBaudRate | `sub_574FE0` | `FT_SetBaudRate` |
| SetDataCharacteristics | `sub_575020` | `FT_SetDataCharacteristics` |
| SetDtr / ClrDtr | `sub_575060` / `sub_575090` | `FT_SetDtr` / `FT_ClrDtr` |
| SetRts / ClrRts | `sub_5750C0` / `sub_5750F0` | `FT_SetRts` / `FT_ClrRts` |
| Purge | `sub_575120` | `FT_Purge(1)` затем `FT_Purge(2)` |
| SetTimeouts | `sub_575160` | `FT_SetTimeouts` |
| Найти устройство | `sub_574CD0` | `FT_ListDevices` + сравнение описания |

Объект порта: `+12` = handle, `+16` = CString с текстом ошибки, `+20`/`+24` = счётчики
чтения/записи, `+8` = флаг «открыт».

Приём данных с таймаутом: `sub_4030E0` / `sub_403720` — принимают буфер и длину,
ждут побайтово через `sub_574F00`-цикл, копят в **буфере 1024 байта по смещению
`2424910`** (`0x25004E`) в главном объекте, затем вызывают VMT+80 (разбор ответа) и
`sub_402E40` (обработка хвоста/чексуммы).

## 3. Архитектура протоколов (главный результат)

### 3.1 Фабрика протоколов

`sub_5703B0` (9310 байт) — гигантский `switch (id)`:

```c
if ( v4 == 1000 ) { ... }
switch ( v4 ) {
  case 0:   v7 = sub_43D5B0(v34); break;   // -> VMT класса протокола
  case 1:   v7 = sub_44AEE0(v35); break;
  ...
  case 182: ...
}
```

`id` — это **тот самый `id=NNN`** из записей `auto.dll` / `auto2.dll`.
**178 протокольных классов, id 0…182** (с пропусками).

### 3.2 Класс протокола

Каждый класс — объект Delphi с VMT в `.rdata` (диапазон `0x006206FC`…`0x0062423C`),
ставящийся в конструкторе: `*this = &off_XXXXXX`.

Структура VMT (единая для всех):

| Смещение | Назначение |
|---|---|
| `+0` | `sub_44C560` / `sub_458000` — служебное |
| `+4` | `sub_4018C0` или `sub_401D70` — общее |
| **`+8`** | **примитив 1** — init / setup записи |
| **`+12`** | **примитив 2** — erase |
| **`+16`** | **примитив 3** — запись блока |
| **`+20`** | **примитив 4** — close write |
| **`+24`** | **примитив 5** — вспомогательный |
| **`+28`** | **примитив 6** — вспомогательный |
| **`+32`** | **примитив 7** — seed-key (доступ) |
| `+36` | `sub_401D70` / `sub_403620` |
| `+40` | `sub_403620` |
| `+44…+68` | `sub_522960` (возврат 1) / `sub_49C070` (возврат 0) — заглушки |
| **`+0x4C` (76)** | **ТРАНСПОРТ: send/recv(self, buf+len, timeout)** — `sub_403720` (классы с разбором 0x12/0xB8) либо `sub_4030E0` (KWP1281-класс, напр. id=11, 16) |
| `+0x50` (80) | разбор ответа — `sub_403810` (0x12/0xB8) либо `sub_4031D0` (диспетчер KWP1281) |

Проверено побайтово по VMT id=0/1/11/16 (база совпала полностью) —
`work/verify/VERIFICATION.md`.

Извлечено 1315 уникальных адресов методов в `proto-map.json`; **177 из 178**
протоколов получили полный набор из 7 примитивов (id=182 — не протокол, а
fallback-ветка фабрики), у **169** распознаны кадры — 3257 кадров в сумме по
протоколам (**3126 уникальных** в 956 функциях; пересобрано экстрактором v2,
см. `work/verify/AUDIT-2.md`, из них 99,5 % с длиной из `push`).

### 3.3 Оркестратор шага

Типовой поток записи (разобран на `sub_4231C0`):

```
InitWrite2 -> SeedKey -> Erase2 -> Write2 -> CloseWrite2
```
с проверкой `SEED KEY OK`, `ERASE2 OK`, `WRITE2 OK`, `CLOSE WRITE2 OK` и
итальянскими ошибками `ERRORE CHK_WRITE1/2`, `ERRORE CICLO_CHK`, `ERRORE CHK_CLOSE`.

## 4. Извлечённые кадры — примеры

Байты, показанные как `--`, вычисляются в рантайме (адреса, seed/key, счётчики).

### id=0 — BMW DDE4.0 (KWP2000 + SecurityAccess)

```
seed-key  27 01                       <- запрос seed (SID 0x27, sub 0x01)
seed-key  27 02 42 4D 57 17           <- ответ: "BMW" + 0x17  !!!
erase     09 31 02 08 .. 06 ...       <- SID 0x31 StartRoutine
write     B8 12 F1 09 34 0F 00 00 06 00 00 C0 00 AF
close     B8 12 F1 03 30 EB 01 82     <- SID 0x30
```

**Ключ доступа `42 4D 57` = ASCII «BMW»** — жёстко прошит в бинарь.

### id=16 — Fiat ME7.3H4 (короткий формат: байт длины + SID)

```
02 1A 98 00 / 02 1A 99 00 / 02 1A 91 00 / 02 1A 94 00   <- init (sub_49B700)
08 34 -- 40 -- 80 07 C0                                  <- заголовок блока записи
06 -- 56 29 2D BF 6F                                     <- seed-key (ключ вычисляется)
```

Кадры короткого формата — заголовка `82 12 F1` у id=16 нет (исправлено по итогам
перепроверки, см. `work/verify/VERIFICATION.md`).

Канонический KWP2000-пример `82 12 F1 10 85 1A` с ответом `… 83 03 02 50 …`
принадлежит **дизельным EDC15-протоколам** — id 19, 26, 49, 59, 61, 67, 74, 75
(`0x82 0x12 0xF1` — заголовок ISO 14230: формат, адрес ЭБУ, адрес тестера).
Подтверждено псевдокодом `sub_50E3D0` (proto 19): `v18 = {-126, 18, -15, 16,
-123, 26}`. Тот же кадр встречается в расшифрованных логах `EOBD2_LOG/*.gal`
(§8.2) — записанный реальный трафик совпадает с базой.

### id=1 — BMW MSS52/53 (DS2)

```
-- 04
-- 04 0D
```
Короткие кадры DS2 (первый байт — длина).

## 6. Защита

### HASP-донгл (Aladdin)

- `winmap.dll` содержит полный рантайм HASP: `hasp_login`, `hasp_logout`,
  `hasp_encrypt/decrypt`, `hasp_legacy_*`, `API_HASP_STATUS`, `API_READBLOCK`,
  `classic_key_info`, `classic_check_local_port`.
- Строка-ключ (vendor code): `qkBr…(reducted)`, рядом — длинный HASP-капсула
  (`0x651F24`), используемая через `sub_586DD0` → `hasp_login`.
- **Для вашей реплики не нужна**: мы реализуем протоколы сами, а не запускаем
  оригинальное приложение.

### Анти-tamper (`k.dat`)

`GetCheck0(path, base)` считает хеши `\gcheck.dll`, `\EOBD2.exe`, `\winmap.exe` и
пишет их в `k.dat` как `%X\n%X\n%X`. `k.dat` в поставке содержит **5** значений —
значит файл накапливался от нескольких сборок.

### Анти-отладка

В `TTL`-секции — список процессов для детекта:
`smartchk.exe`, `procdump.exe`, `pdumpnt.exe`, `msdev.exe`, `td32.exe`
+ `IsDebuggerPresent`, `CreateToolhelp32Snapshot`, `Process32First/Next`.

### Gcheck.dll

Экспортирует `HaspDecrypt` / `HaspEncrypt`, секция `.protect` — 1.46 МБ при
энтропии 8.0 (полностью зашифрована), расшифровывается в рантайме.

## 7. Инфраструктурные функции (для реплики)

| Функция | Что делает |
|---|---|
| `sub_4018C0` | XOR-чексумма: XOR всех байт, результат в последний байт |
| `sub_4030E0` | Приём с таймаутом, буфер 1024 б по смещению `2424910` |
| `sub_4031D0` | Диспетчер ответов KWP1281: `0x01, 0x0A, 0x10, 0x11, 0x12, 0x13, 0x15, 0x7A, 0xD0` |
| `sub_574FE0` | `FT_SetBaudRate` — смена скорости в рантайме |
| `sub_5811F0` | Задержка (double мс) |
| `sub_574FE0(10400)` | Типовое переключение на 10.4 кбод |

Ошибки протокола (полный список — в `01-recon/strings-EOBD1260.exe.txt`):
`ERRORE RINIT1..6` (лестница скоростей), `ERROR Flash:29F400BT CHANGE DRIVER`

`SET_ECU`, `DIS_INT` (запрет прерываний), `ERRORE FORMAT1`, `ERRORE ERASE2`.

## 8. Открытые вопросы

1. **`chk/*.chk` (148 файлов, 197–624 б)** — зашифрованы. Установлено:
   - байты 0–6 одинаковы во всех файлах: `44 8B C3 D1 AD 8D 4C`, байт 7 = `0x92…0x9B` (10 вариантов);
   - смещения 10–23 принимают лишь **3** различных значения — фиксированные поля;
   - **ноль** байтов `0x00` во всех 41 КБ — простой XOR исключён (IC 0.007);
   - имена файлов (`AudiMe7`, `Vw110`, `BoschME744`) **не встречаются** ни в одном
     бинаре, строка `.chk` в EXE отсутствует (единственное вхождение `chk` —
     `smartchk.exe` в списке анти-отладки);
   - ⇒ файлы не открываются по имени из EXE/DLL; вероятно, читаются кодом из
     зашифрованной `.protect` секции `Gcheck.dll` либо это данные сопутствующего
     инструмента. Требует динамического анализа (запуск под отладчиком).
   - Состав расширений: 145 `.chk` + `0Bosch8Bit.gen` + по одному `.ch1`/`.ch2`.
   - Структура (перепроверка 2026-10-14): байт 7 ∈ `0x92…0x9B` (10 значений,
     `0x93` × 30 файлов), байт 8 ∈ `{0x31, 0x54…0x5D}`; байты 10–23 принимают
     ровно **3** варианта, и по ним файлы чётко делятся на группы 117/16/15 —
     похоже, 3 типа записей. Первые байты (`44 8B C3 D1 AD 8D 4C`) дизассемблируются
     как правдоподобный x86 (`44 8B C3` = `mov r8d, ebx`) — вероятно, это бинарный
     формат (возможно, с обфускацией), а не шифртекст текста.
   - Новая зацепка (перепроверка 2026-10-14): расшифрованные логи `EOBD2_LOG/*.gal`
     (`work/verify/gal-decoded/`) — поискать в них имена `chk`-профилей и связь
     с `apertura.dat`.

2. ✅ **`EOBD2_LOG/*.gal` — РЕШЕНО (перепроверка 2026-10-14)**: логи не шифрованы,
   а обфусцированы XOR с одним байтом `0x1C`. После декодирования читаются
   KWP2000-сессии и блоки идентификации ЭБУ: Fiat (`82 12 F1 10 85 1A`),
   VAG (`82 12 F3 10 85 1C`, `0281010161… SmartEDG15C-5.1`), Opel
   (VIN `W0L0TGF08X…`). Прежние «повторы `E3`, `2C`» = `0xFF^0x1C` (padding) и
   `'0'^0x1C` (цифры). Заявленная «энтропия 7.95» не воспроизводится: текстовые
   логи 6.2–7.2, near-uniform 8.0 — один бинарный лог. 15 логов декодированы
   (`work/verify/gal-decoded/`), отчёт — `work/verify/VERIFICATION.md` §2.
   Логи — готовый материал для валидации кадров базы на реальном трафике.

3. **`apertura.dat`** — формат читается, но семантика записей (что именно ищется
   по этим 8-байтовым паттернам) не подтверждена на живом образе.

4. **Полнота кадров**: извлечены все *константные* байты. Байты, вычисляемые в
   рантайме (адреса, seed/key, счётчики), помечены `--`; для их восстановления
   нужно читать псевдокод соответствующего метода (`dump/funcs/*.c`).
   ✅ **Решено аудитом-2 (2026-10-15) и экстрактором v2**: кандидат «ложной дырки»
   подтверждён (в write-кадре id=0 позиция 2 — константа `F1`, ставится через
   `dl`), и найдены ещё родственные дефекты извлечения: ложные `--` для сторов
   через байтовые регистры, слияние взаимоисключающих ветвей, длина кадра из
   протяжённости записей вместо `push imm`, потерянные send-сайты. Экстрактор
   `extract_frames.py` переписан (per-path символьное исполнение, длина из
   `push`, ловля байтовых регистров и raw-esp сторов), база пересобрана.
   Отчёт — `work/verify/AUDIT-2.md`.

## 9. Что дальше (маршрут до рабочего загрузчика)

1. Взять один протокол и вручную добить рантайм-байты по его псевдокоду.
   Кандидаты: **id=19** (Peugeot EDC15C2 — канонический KWP2000, есть совпадающие
   декодированные логи) или **id=16** (Fiat ME7.3H4 — короткие кадры, простые).
2. Поднять стенд: ЭБУ на столе, 12 В, K-line, FT232.
3. Прогнать read-only шаги (идентификация, чтение) через `10-replica/src/loader.py --live`,
