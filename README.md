# EOBD1260 — база протоколов ЭБУ и открытый загрузчик

Спецификации протоколов чтения/записи ЭБУ, извлечённые статическим анализом
итальянского флешера **EOBD1260** (он же Galletto 1260 / EOBD2), плюс
самостоятельный загрузчик под обычный **K-line адаптер на чипе FTDI** —
**без донгла, без оригинального ПО**.

> Здесь **нет** файлов самого вендорского продукта. Репозиторий содержит только
> результат обратного инжиниринга: описания протоколов, базу совместимости ЭБУ,
> документацию и собственный код. Это материалы для совместимости — ровно то,
> для чего реверс-инжиниринг и делается.

## Быстрый старт

Зависимостей нет — только CPython и `ftd2xx.dll` (ставится с драйвером адаптера,
либо кладётся рядом).

```bash
cd src

# найти адаптер
python ftdi_d2xx.py

# список протоколов
python loader.py protocols

# что умеет конкретная марка
python loader.py protocols --profile bmwms4

# кадры конкретного протокола (без железа)
python loader.py show 0
python loader.py show 16

# прогон шага по кабелю: сначала вхолостую, потом по-настоящему
python loader.py probe 16 --step seed-key
python loader.py probe 16 --step seed-key --live --baud 10400
```

## Как устроены протоколы

Оригинал общается с кабелем только через `ftd2xx.dll` (13 функций D2XX), причём
`FT_SetBitMode` не используется: уровни K- и L-линии формируются линиями
**RTS/DTR**. Отсюда два режима в `ftdi_d2xx.py`:

- `send_5baud(addr)` — медленная инициализация ISO 14230 (старт-бит, 8 бит
  LSB-first, стоп-бит, 200 мс на бит);
- `k_line_pulse(level, sec)` — импульсы для быстрой инициализации.

У каждого протокольного класса семь примитивов:

| Смещение | Роль |
|---|---|
| `+8` | init / setup записи |
| `+12` | erase |
| `+16` | запись блока |
| `+20` | close write |
| `+24`, `+28` | вспомогательные |
| `+32` | seed-key (доступ) |

Кадры в базе — шаблоны. Константные байты даны как есть, рантайм-байты (адреса,
seed/key, счётчики) — `null`. `Frame.render(...)` отказывается отправлять кадр с
незаполненной дырой, чтобы нельзя было случайно послать мусор.

### Пример: BMW DDE4.0 (`id=0`)

```
seed-key  27 01                       запрос seed (KWP2000 SecurityAccess)
seed-key  27 02 42 4D 57 17           ответ: "BMW" + 0x17
erase     09 31 02 08 .. 06 ..
write     B8 12 F1 09 34 68 00 00 06 00 00 C0 00 AF
close     B8 12 F1 03 30 EB 01 82
```

### Пример: Fiat ME7.3H4 (`id=16`) — короткие кадры (байт длины + SID)

```
02 1A 98 00 / 02 1A 99 00 / 02 1A 91 00 / 02 1A 94 00   init (sub_49B700)
08 34 -- 40 -- 80 07 C0                                  заголовок блока записи
06 -- 56 29 2D BF 6F                                     seed-key (ключ вычисляется)
```

Канонический KWP2000-пример `82 12 F1 10 85 1A` принадлежит дизельным
EDC15-протоколам (id 19, 26, 49, …) — у `id=16` заголовка `82 12 F1` нет.

## Логи сессий (`.gal`) вскрыты

Вендорская программа писала логи сессий в `EOBD2_LOG/_eobd2_*.gal` — они
оказались не зашифрованы, а обфусцированы **XOR с одним байтом `0x1C`**.
После декодирования в логах виден реальный K-line трафик: кадры ISO 14230 /
KWP2000 (`82 12 F1 10 85 1A` — StartDiagnosticSession, ответы `82 F3 12 50 …`)
и блоки идентификации ЭБУ (номера Bosch/VAG, VIN). Декодер —
[`tools/gal_decode.py`](tools/gal_decode.py); подробности и доказательства —
[`docs/VERIFICATION.md`](docs/VERIFICATION.md) §2.

Это ценный материал для стендовой проверки: в логах есть записанные сессии с
ответами, с которыми можно сверять поведение реплики.

## Перепроверка (2026-10-14)

Все ключевые утверждения репозитория заново выведены из сырых артефактов
вендорского пакета — 71 автопроверка, **70 PASS / 1 FAIL**. Итоги и список
найденных дефектов: [`docs/VERIFICATION.md`](docs/VERIFICATION.md).
Аудит-2 (2026-10-15) нашёл и закрыл дефекты извлечения кадров — экстрактор
переписан (v2), база пересобрана, реплика отказывается отправлять кадры без
подтверждённой длины: [`docs/AUDIT-2.md`](docs/AUDIT-2.md) §3, §7.
Воспроизведение: распакуйте пакет EOBD1260 в каталог и выполните
`python tools/verify_claims.py <каталог_пакета>`.

Побайтово сверено с базами IDA: VMT четырёх классов (все 28 примитивов),
`switch`-фабрика `id → класс` (178/178, 0 расхождений), XOR-чексумма
`sub_4018C0`, заглушка `Check0` в `winmap.dll`. Известный пробел: 3 профиля
ЭБУ (`BMWMINID`/45, `SEATEDC15V`/56, `VWEDC15P`/27) не имеют протокольного
класса — id 27, 36, 45, 56, 87 отсутствуют в фабрике.

## Безопасность при работе с ЭБУ

Запись и стирание — **только на стендовом блоке** (12 В, K-line, масса), никогда
на машине без явного согласия владельца. Рекомендуемый порядок:

1. read-only: инициализация и идентификация, сверка ответов с оригиналом;
2. идемпотентная запись в заведомо пустую область (`0xFF`) с чтением назад;
3. полный цикл с бэкапом и восстановлением;
4. acceptance-лог (хеш образа) — сохранить.

Всегда держите под рукой план восстановления: как выйти из pending-состояния и
чем поднять блок, если сессия оборвётся.
